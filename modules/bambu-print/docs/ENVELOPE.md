# 信封（BBX1）：一段只能用一次的密文

**结论**：网页用它加密，机器人用它解密。一段只能解一次，过期作废；解不开时只告诉你「解不开」，不会告诉你是哪一位错了。格式改一次，网页和服务端要同时改，老网页会被拒。

为什么要有它、用户怎么走一遍，看 [ENROLL.md](ENROLL.md)。这里讲的是这段文本本身。

## 1. 它长什么样

`BBX1.<base64url(二进制)>`

- 开头四个字符固定是 `BBX1`，后面一个点。
- base64url 用 `A-Za-z0-9-_`，不带 `=` 填充。解析时会容忍首尾空白、换行、全角空格，也接受标准 base64 的 `+` 和 `/`（有些工具会帮你转一道）。
- 整段文本上限 4096 个字符，超过直接报 `TOO_LARGE`，不进解码。
- 只有一种用途：**登录**。里面必须有 Bambu 账号和密码，少一个就是 `BAD_PAYLOAD`。

## 2. 为什么用公钥

一句话：网页只需要「能加密」，机器人需要「能解密」，这两个能力必须分开。

| 方案 | 问题 |
|---|---|
| 对称加密，网页里放同一把钥匙 | 网页是公开的，谁都能拿钥匙解开 |
| 对称加密，用口令派生 | 机器人不知道口令就解不开，等于没解决「密码不进聊天」 |
| 公钥加密（现在这个） | 网页只有公钥，只能加密；私钥只在这台机器上 |

密钥是 P-256 的 ECDH 对：

- 公钥是 65 字节的未压缩点（`0x04 || X(32) || Y(32)`），base64url 之后 87 个字符，放在链接的 `#k=` 后面。
- 私钥是 JWK，存在数据目录的 `bbx-key.json`（0600），永不导出、不进聊天 / 面板 / 日志。
- 公钥指纹 = SHA-256(公钥那 65 字节) 的前 4 字节，转成 8 位十六进制。网页「第一步：确认公钥」里显示的指纹，和面板显示的是同一串；对不上就说明页面不是这台机器给的。

换一把私钥（现在的代码里只有 `envelope.rotate()`，没有入口）等于换一把锁：所有旧链接和还没用的信封立刻作废。这是有意设计的，不是 bug。

## 3. 外层二进制

总长 = 99 字节头 + 密文 + 16 字节 GCM tag。

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | magic | ASCII `BBX1` |
| 4 | 1 | ver | `1` |
| 5 | 1 | suite | `1` 表示 P-256 ECDH + HKDF-SHA256 + AES-256-GCM |
| 6 | 65 | ephemeral | 一次性 P-256 公钥，未压缩点，首字节必须是 `0x04` |
| 71 | 16 | salt | HKDF 的 salt |
| 87 | 12 | iv | AES-GCM 的 nonce |
| 99 | n | ciphertext | 明文 body 的密文 |
| 99+n | 16 | tag | GCM 认证标签 |

- **AAD 就是前 99 字节**（magic 到 iv）。改任何一个字节，解密都会失败，报 `BAD_TAG`。
- 二进制下限 99 + 1 + 16 字节，上限 99 + 4096 + 16 字节。
- 版本或套件不认识，分别报 `BAD_VERSION` / `BAD_SUITE`；临时公钥首字节不是 `0x04` 报 `BAD_FORMAT`。

## 4. 密钥怎么派生

```
shared = ECDH-P256(网页生成的一次性私钥, 机器人公钥)     // 32 字节
prk    = HKDF-Extract(salt, shared)
key    = HKDF-Expand(prk, info = "bambu-print/envelope/v1", 32)
```

然后 AES-256-GCM，12 字节 IV，16 字节 tag。

两个实现细节，改代码时别踩：

- info 必须逐字节等于 `bambu-print/envelope/v1`（UTF-8）。
- WebCrypto 要**分两步**：先 `deriveBits` 拿 ECDH 结果，再 `importKey('raw', ..., 'HKDF')`，最后 `deriveKey({ name: 'HKDF', hash: 'SHA-256', salt, info }, ..., 'AES-GCM')`。一步链式在 Chrome / Firefox 能跑，Node 会报 `Unsupported key usage for a HKDF key`。`assets/enroll/bbx.js` 里是为这个专门写成两步的。

## 5. 明文 body（BBXB v1）

定长 33 字节，后面跟两个「2 字节长度 + 内容」的字段。多字节整数都是大端。

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | magic | ASCII `BBXB` |
| 4 | 1 | bodyVer | `1` |
| 5 | 1 | flags | 固定 `2`（表示带账号）。只做一致性校验，真正判定看字段长度 |
| 6 | 4 | iat | 签发时间，Unix 秒（u32） |
| 10 | 4 | exp | 失效时间，Unix 秒（u32） |
| 14 | 2 | ttlMin | 生存时间，分钟（u16），1~1440 |
| 16 | 1 | region | `0` = us，`1` = eu，`2` = cn |
| 17 | 16 | jti | 一次性随机值，服务端靠它防重放 |
| 33 | 2 | accountLen | 账号 UTF-8 字节数，1~200 |
| .. | * | account | 账号（邮箱或手机号） |
| .. | 2 | passwordLen | 密码 UTF-8 字节数，1~256 |
| .. | * | password | 密码 |

几个约定：

- 账号在网页端会 trim；密码**一个字符都不动**，首尾空格也可能是密码的一部分。
- `exp` 必须大于 `iat`；两个都按服务端自己的时钟判，服务端不会重算 `iat + ttlMin × 60`。
- 解码后如果还有剩余字节，报 `BAD_PAYLOAD`（尾部多了东西）。
- 区域默认中国大陆：网页的 `DEFAULT_REGION` 是 `cn`，编码时没传 region 也按 `cn`。

## 6. 服务端怎么判：密钥、时间、一次性

策略都在 `lib/envelope.mjs`，加解密本身一行都不在这里写：它 `import` 网页那份 `assets/enroll/bbx.js`。**只有一份实现**，所以浏览器和 Node 的行为逐字节一致，互操作测试也是这么做的。

### 私钥文件

- 首次用到时生成 `bbx-key.json`：`{ v: 1, alg: "P-256", createdAt, publicKey, privateJwk }`，0600，临时文件加改名。
- 文件不存在 → 生成新的；文件存在但坏了 → `BAD_KEY`，**绝不静默重建**。静默换钥会让用户手里所有链接和信封突然全废，而且没人知道。
- 校验很严：版本、alg、kty、crv、d/x/y 都会检查；私钥算出来的公钥必须和文件里记的 `publicKey` 一致。对不上比文件坏更隐蔽，直接当坏文件处理。

### 时间

- 时钟偏差容忍 `SKEW = 120` 秒。
- `now > exp + 120` → `EXPIRED`。
- `iat > now + 120` → `NOT_YET`（两边时钟差太多）。
- `ttlMin` 超过设置 `enrollMaxTtlMinutes`（1~1440，默认 1440）→ `BAD_PAYLOAD`，提示里会写出「你这个多少分钟、本机上限多少分钟」。
- 网页现在固定 10 分钟，所以正常情况下撞不到上限。设置 `enrollTtlMinutes`（默认 60）只用于面板展示「建议生存时间」，网页不读它。

### 一次性

- 解密成功、时间检查通过后，先把 `jti` 记进 `bbx-used.json`，再把明文交出去。所以「解开」就等于「用掉」，后面登录失败也算用掉。
- 同一个 `jti` 再来一次 → `REPLAYED`。查重和写盘在同一条队列里，两个请求同时提交也只可能成功一次。
- 多个进程 / 多实例共用同一个数据目录时，写入前会再读一次盘，能看见别人刚记下的 jti。
- 已用记录文件 `{ v: 1, used: { jti: exp } }`，0600。`exp` 过去超过 24 小时的条目会被清掉；超过 5000 条时按 `exp` 淘汰最旧的。
- 文件坏了会告警，然后**按空处理**：重放保护被重置。这是一个已知代价，不是「解不开」。
- 写盘失败不回滚内存记录：宁可这一次报 `IO`，也不让同一个信封在本进程里用两次。

### 只看看、不消费

`inspect()` 只解密、只校验时间和结构，不记 jti、不执行登录，账号一律打码（`a***@b.com` / `138****8000`）。面板「登录信封」页的「解析」按钮用的就是它，看完这段还能照常拿去用。过期的信封连预览也会报 `EXPIRED`，因为时间和有效期是同一套判定。

### 明文只在调用栈上

`open()` 会返回 `account` 和 `password`，因为 `index.mjs` 要拿它们去登录云端。这是信封流程里唯一允许出现明文的地方（面板的 `/login` 是另一条独立路径，它收的是用户自己表单里的账号密码）：

- 它不进 `inspect()` 的返回，不进日志，不进审计备注，不进任何路由响应，不写盘。
- `applyEnvelope()` 用完在 `finally` 里把这两个字段置空。
- 一次性在返回明文**之前**就记好了，所以不存在「明文已经交出去、jti 还没记上」的窗口。

## 7. 为什么只能解一次

密文躺在聊天记录里，光靠「过期」不够：有效期内足够被人翻出来重放一次。所以要给每段一个随机 `jti`，用过的记账，第二次直接拒。

代价是：**粘错地方、机器人重启、登录失败，都可能让这段白生成**。只要机器人成功解开，它就算用掉了，只能重新生成。这是有意的取舍，不是毛病。

跨机器：每台机器有自己的私钥，发给 A 机器的信封 B 机器解不开（`BAD_TAG`）。两台机器如果共用同一个数据目录，会共用同一份已用记录。

## 8. 为什么会过期

- 缩短「密文躺在聊天里还能用」的时间窗。网页固定 10 分钟，够走完「生成 → 复制 → 粘回私聊」。
- 过期不等于从聊天里消失。那段文字还在，只是没人能再用它。
- 本机时钟不准会出事：慢了可能提前 `EXPIRED`，快了可能 `NOT_YET`。先对一下系统时间。

## 9. 解不开时你看到什么

聊天和面板的措辞会有一点点不同，意思一样；下面这些是聊天里的大意。

| 错误码 | 什么时候出现 | 你会看到（大意） | 下一步 |
|---|---|---|---|
| `BAD_FORMAT` | 不是 `BBX1.` 开头、内容不完整、临时公钥格式不对 | 这段不像是这台机器生成的登录信封（应该以 BBX1. 开头，整段复制，别只复制一半） | 重新复制整段 |
| `BAD_VERSION` | 版本号不是 1 | 信封版本不支持，刷新一下登录网页再生成 | 刷新网页（旧的标签页） |
| `BAD_SUITE` | 套件号不是 1 | 信封的加密套件这台机器不支持 | 刷新网页后重新生成 |
| `TOO_LARGE` | 超过 4096 字符或二进制过长 | 这段太长了，不像是信封 | 确认粘的是信封，不是整篇聊天记录 |
| `BAD_TAG` | 被改过、不是给这台机器的、私钥换过了 | 这段信封解不开：可能不是给这台机器的，或者内容被改过 | 重新要链接生成 |
| `BAD_PAYLOAD` | 字段不合法：缺账号 / 缺密码 / 时间字段不对 / 超上限 / 尾部有剩 | 信封内容不正确 | 重新生成；还不行就是版本不匹配 |
| `EXPIRED` | 超过 `exp + 120` 秒 | 信封过期了，重新生成一段 | 重来，别生成完先去干别的 |
| `NOT_YET` | `iat` 比本机时间还晚 120 秒以上 | 信封的签发时间比本机时间还晚，请检查两边的时钟 | 对时间，或重新生成 |
| `REPLAYED` | 这个 jti 已经用过 | 这个信封已经用过了，请重新生成 | 重新生成 |
| `NOT_READY` | 私钥还没加载 | 登录密钥还没就绪 | 让主人看面板「登录信封」 |
| `NO_CRYPTO` | 运行环境没有 WebCrypto | 当前环境不支持 WebCrypto，信封功能不可用 | 换环境（Node 22 或现代浏览器） |
| `BAD_KEY` | 私钥文件坏了 / 公钥和私钥对不上 | 登录私钥损坏，已拒绝自动重新生成 | 需要人工处理，别直接删 |
| `BAD_INPUT` | 参数类型不对（比如传的不是文本）、登录网页地址不合法 | 参数不正确（或地址必须以 http:// 或 https:// 开头） | 按提示改 |
| `IO` | 读写数据目录失败 | 读写信封数据文件失败（检查数据目录的权限） | 查权限 |

规则：**不在允许表里的内部错误一律折算成 `IO`**，话术换成中文。这样不会把内部细节、英文异常、文件路径漏给用户。

网页端自己也有几句话：浏览器没有 WebCrypto、公钥不是 87 个字符、表单没填完。它们只影响生成，不影响解密。

## 10. 改格式要动哪些地方

| 地方 | 要改什么 |
|---|---|
| `assets/enroll/bbx.js` | 常量 `MAGIC / BODY_MAGIC / VERSION / SUITE / KDF_INFO / MAX_*`，`encodeBody / decodeBody / sealEnvelope / openEnvelope` |
| `lib/envelope.mjs` | 不写加解密，只改策略：私钥文件校验、时间、一次性、对外返回形状、允许的错误码 |
| `assets/enroll/index.html` + `enroll-form.js` | 页面固定 10 分钟、区域默认 `cn`、表单校验 |
| `test/envelope.test.mjs` | 互操作、篡改、过期、重放、换钥、仅内存模式 |
| `test/enroll-page.test.mjs` | 页面静态检查（不联网、不存本地、没有安全码输入框） |

版本纪律：改了字节布局就把 `VERSION` 加一，换了加密算法就把 `SUITE` 加一。服务端会分别报 `BAD_VERSION` / `BAD_SUITE`，网页提示用户刷新，比「静默解不开」好排查。

## 11. 已知边界

- **私钥默认在磁盘上**（`bbx-key.json`）。能读数据目录的人能解开任何拿到的信封，也能解开保险箱。这条挡的是「事后翻聊天记录」，不是「本机管理员」。
- 仅内存模式（`keyMode: 'ephemeral'`）可以让磁盘上没有私钥，代价是重启后旧链接全废；而且这个开关没有做进面板，只有部署参数能改。
- 运行期间 dump 进程内存、改代码：这两条不解决，任何本机解密的方案都一样。
- 静态页面被替换 / 被 fork 改坏：能偷用户输入（用户本来就要在里面填），偷不到私钥；认指纹或自己部署。
- `bbx-used.json` 损坏时重放保护会被重置（会告警）。这是为了「坏文件不挡登录」做的妥协。
- 时钟偏差超过 120 秒会误报过期或未生效。
- 信封不携带「给哪台机器人」的标识，靠「解不开」来区分（`BAD_TAG`），所以话术只能是「可能不是给这台机器的」。
